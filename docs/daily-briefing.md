# 每日企业 AI 简报：研究与发布约定

下列约定适用于本网站和现有 Enterprise AI Field Notes 任务。上海日期决定资料截点；补刊署实际补写日期。稿件未完成时，应保存研究进度，不能进入正式索引。

## 每日执行入口

1. 先在新检出的 Sites 源码运行 `node scripts/briefing-status.mjs`，按需传 `--from YYYY-MM-DD --to YYYY-MM-DD`。与 GitHub 的索引和 Sites 版本比对；本地存在文件不等于发布。
2. 没有当期权威稿时，同时检索几种来源，先写下选中的直接链接、原始发布日期、关键数字及其分母；针对每个业务问题确认一手出处和局限。把真实进度存到 `content/recovery/YYYY-MM-DD.md` 并提交至源码仓库；不等待全篇写完才首次保存。续跑先读这个文件。此目录不会生成站点文章。
3. 选齐四组即可编辑。以同一份中文稿为权威来源，完成英文翻译及结构化数据。把完整 Markdown 放入 `content/sources/`，再用 `node scripts/upsert-briefing.mjs <候选 JSON 路径>` 入库并运行 `npm run validate:content`。从 2026-11-12 起，这个命令还会核对原稿边界、日期、文章、字数及结尾栏目与 JSON。不要改动校验以迁就不合格的稿子。
4. 按下列发布约定核验两个仓库并部署；服务端回应成功之后才报已发布。若合格原稿还在仓库里但未部署，继续从该稿发布。不要把调度器的 completed 字段当成发布回执。缺少硬错误且读写正常时继续编辑，不以“尚未写完”作为停止原因。

## 完整编辑与发布约定

【执行与交付优先规则】
这是在当前绑定对话中执行的完整研究与发布任务，必须连续完成检索、编辑、校验、网站内容入库、GitHub同步、站点部署和发布确认，不得把发布交给其他对话或要求用户转贴。每次触发都必须执行研究并发送明确结果，不能因周末、无突发新闻、昨天已有报告、用户未在线或尚未人工催促而静默跳过。
以 Asia/Shanghai 当地运行日期作为本期日期；昨天的正文不能作为今天完成的证据。先检查当前日期是否已有完整、通过协议校验的本期正文；存在则不重新选题，必要时重发该完整正文供恢复导入。
当工具不可用、研究失败、资料不足、无法完成校验或执行中断时，也必须发送可见的《企业AI简报生成异常｜YYYY-MM-DD》：明确失败阶段、实际已完成事项、缺失项、可恢复的来源及下一步。异常说明不得伪装成正常 SITE_ISSUE，不能输出空报告或把旧报告改日期。不要使用静默/no_update作为这些情况的交付方式。
成功时只发送一份完整的站点内容块；最后一个栏目之后才关闭边界，不能在边界外补 takeaways 或 contrarian。保留下面所有研究与栏目约束。

作为 AI Field Notes 的唯一研究与编辑内容源，检索并筛选 4–6 组值得关注的企业 AI 资料，重点关注 Agent、RAG、真实部署、工作流改造、评估、安全、权限、Human-in-the-loop 与可验证业务价值。优先选择小而具体的业务问题，避免宏观炒作。

来源应尽量多样，包括独立新闻、同行评审论文、工程博客、开源仓库、数据集、标准、监管材料、演示视频、播客或访谈；不要为了媒介数量加入低质量材料。重要主张尽量使用独立来源或不同类型来源相互验证，并明确区分确认事实、厂商主张、独立证据、编辑推断与尚未证明的内容。

保留此前简报已经形成的选题质量、跨来源检索、多媒介覆盖、证据分级和项目导向。优先选择自上一期后发布或实质更新的资料；不重复往期资料，除非存在实质更新，并明确说明更新内容。没有足够高质量当日新资料时，扩大到最近7天，再到此前未覆盖的高质量资料，并明确实际发布日期；仍不足时如实发送不足说明，不编造、不重复凑数。

每期只生成一份权威 Markdown 简报，站点JSON与英文译文从这份权威内容转换，不能让其他任务再次总结或改写事实。内部必须保存站点要求的结构化JSON；不在给用户的回复中额外粘贴重复的长JSON。标题、入选篇目、数字、链接和证据等级构成该期的权威版本。
